## Video Editor (`my_scripts/video/video_editor.py`)
General-purpose quick-edit script, meant as the base for more one-off editing operations later - unlike the other `video/` scripts (which each do one specific job), this one composes several independent, optional operations in a single ffmpeg pass:
- **Watermark/logo overlay** (`--watermark_path`, `--watermark_position top-left|top-center|top-right|bottom-left|bottom-center|bottom-right|center`, `--watermark_scale` as a fraction of output width (now a slider/field in both UIs, not just a CLI-only flag), `--watermark_opacity` 0.0-1.0, default 1.0 = fully opaque) - geometry (size/position, aspect-ratio preserved) is computed in pure Python (`utils/video/video_editor.py`) from the watermark image's real dimensions, not guessed. Both UIs show a live preview of this before you run anything, using the same `compute_watermark_geometry()`/`resolve_output_dimensions()` the real ffmpeg command uses - so what you see is what the render will produce, not an approximation - and updates live as you change the watermark file, its position/scale, or the vertical/horizontal toggle. `--watermark_opacity` applies `format=rgba,colorchannelmixer=aa=X` before the overlay (the same technique `rocket_shorts_publisher.py` already used) - ignored with `--hwaccel`, since the `nv12` pixel format the watermark gets converted to there before `overlay_cuda` has no alpha channel at all, so there's no way to express partial transparency on that path without dropping back to CPU (which would defeat the point of `--hwaccel`); the render still succeeds, just fully opaque.
  - **Free placement by dragging the preview** (`--watermark_x`/`--watermark_y`, both required together, each a 0.0-1.0 fraction of output width/height for the watermark's *center*) - overrides `--watermark_position` entirely when both are set, for a spot no fixed preset covers. Both UIs let you just drag the watermark thumbnail around directly on the live preview instead of typing fractions by hand (desktop: a Tkinter drag on `wm_preview_label`; web: a `mousedown`/`mousemove`/`mouseup` drag on `#wmPreviewImg`) - dragging derives the center fraction from wherever you drop it and writes it back into the same fields. Using the *center* rather than the top-left corner means changing the scale afterward doesn't shift the point you actually dragged to. Picking a position from the dropdown again clears the custom fraction so the preset takes over; a dedicated "↩️ בטל מיקום מותאם"/"clear custom position" button does the same without touching the dropdown.
- **Old watermark removal/replacement** (`--remove_watermark_position` with the same position choices, `--remove_watermark_width_fraction`/`--remove_watermark_height_fraction` as fractions of the *input's* own width/height, default 0.2/0.12) - erases that rectangular region with ffmpeg's `delogo` filter, run at the input's native resolution before any scaling. This blurs/interpolates the region from its surroundings rather than reconstructing genuinely hidden detail - clean on simple backgrounds, a visible soft patch on busy/detailed ones. Combine with `--watermark_path` (same run) to place a new logo over the erased area, or anywhere else - that's a "replace watermark A with watermark B" edit in one pass, not two separate scripts.
- **Vertical conversion** (`--vertical`) - same 1080x1920 TikTok/Shorts crop as `timelapse_maker.py`, or 1920x1080 horizontal (default) otherwise. `--smart-crop` (vertical only, ignored otherwise) picks where that crop window sits instead of always centering it - `utils/media/smart_crop.py`'s `compute_horizontal_crop_offset()` samples ~40 frames, tracks where most of the motion happens via optical flow, and returns a -1.0 (all the way left) to 1.0 (all the way right) offset baked directly into the `crop` filter's `x` expression, so action happening off-center doesn't get cut off by a naive center crop. A failed analysis (or none requested) falls back to the original centered behavior exactly. See `--blur-background` below for a way to convert to vertical *without* cropping the source at all.
- **Blurred background instead of black bars, or fitting a horizontal source into a vertical frame without cropping** (`--blur-background`, without `--hwaccel`, ignored otherwise) - when the source doesn't natively fill the output frame and would otherwise get plain black padding, this fills the whole frame with a scaled-up, cropped, and blurred (`gblur`) copy of the same source instead, with the normally-scaled content (aspect-ratio preserved, never cropped) centered on top (`split` into two branches + `overlay`, a small filter sub-graph rather than the simple linear chain the other options use). Works the same regardless of orientation, so combined with `--vertical` it's the way to place a horizontal (16:9) recording into a 9:16 TikTok/Shorts frame *without* cutting off its sides the way the normal `--vertical` crop would - the full width fits, and the blurred backdrop fills the letterbox bars above/below instead. `--smart-crop` is ignored (logged) when combined with `--blur-background`, since nothing gets cropped at all in that mode - there's no crop window left to reposition. Not available with `--hwaccel` (`gblur` has no proven CUDA equivalent in this project's ffmpeg build).
- **Timelapse speed-up** (`--target-seconds`) - reuses `utils/media/timelapse.py`'s speed/atempo logic exactly; 0 (default) leaves the original speed untouched.
- **Trim range** (`--trim-start <seconds>`, `--trim-duration <seconds>`) - cuts the clip down to a sub-range before any other processing, using `-ss`/`-t` as *input* options (fast seek, applied only to the main video input, not to a watermark image passed alongside it) rather than re-encoding the whole file first. `--trim-duration` alone (no `--trim-start`) trims from the end; a range that would leave nothing after clamping to the file's actual length is skipped with an `[ERROR]` rather than attempted. `--trim-silence` is the automatic alternative - runs ffmpeg's `silencedetect` filter first (audio-only, fast, discarded output) to find silence specifically at the very start/end of the clip (not in the middle - this trims, it doesn't strip mid-clip silence generally) and computes the same kind of range automatically; combining it with an explicit `--trim-start`/`--trim-duration` is ignored in favor of the explicit range (logged, not an error).
- **Denoise / sharpen** (`--denoise` applies `hqdn3d` before scaling, `--sharpen` applies `unsharp` after) - both ignored with `--hwaccel` (no CUDA equivalent used in this project). Useful for cleaning up compressed/noisy capture footage, or crisping up output that got a bit soft from scaling.
- **Skip redundant scale** - if the source is already at *exactly* the target resolution (1920x1080 horizontal / 1080x1920 vertical, or the effective target when `--preserve-resolution` is active - see below), the `scale`/`pad`/`crop` step is skipped entirely (logged) instead of re-processing pixels that wouldn't actually change - only without `--hwaccel` (skipping the CUDA scale step would leave frames in an unverified state for the filters after it, not worth the marginal gain).
- **Preserve source resolution instead of forcing 1080p** (`--preserve-resolution`) - by default the output is always resized to the fixed 1920x1080 (horizontal) / 1080x1920 (vertical) box regardless of the source, which means a 4K (or higher) recording gets quietly downscaled. This flag makes `resolve_effective_output_dimensions()` (`utils/video/video_editor.py`) derive the target from the source's own probed dimensions instead: horizontal output becomes an exact pass-through of the input's own width/height (rounded up to even, since codecs require even dimensions for 4:2:0 chroma subsampling) - no resize/pad at all; vertical output still crops to a 9:16 box (that's the entire point of `--vertical`), but the box is sized from the source's own resolution (its larger dimension becomes the crop box's height) instead of a fixed 1080x1920, so a higher-than-1080p source doesn't get needlessly shrunk during the crop. A source already smaller than the fixed defaults isn't upscaled either way - "preserve" never means "enlarge."
- **Skip the `_edited_horizontal`/`_edited_vertical` output filename suffix** (`--no-suffix`) - by default every output is named `<source>_edited_horizontal.mp4`/`<source>_edited_vertical.mp4` to make source vs. output obvious even if they ever end up side by side. This flag names it `<source>.mp4` exactly instead - outputs already always land in a separate `workspace/studio/<orientation>/` folder from the source, so there's no risk of a name collision with the original file even without the suffix.
- **Export codec** (`--codec h264|hevc|av1`) - `h264` is CPU (`libx264`, universal compatibility), `hevc`/`av1` use NVENC (GPU, requires an NVIDIA card) at settings matching the quality presets already used by `rocket_shorts_publisher.py`. `--nvenc-preset p1`-`p7` and `--nvenc-cq <n>` override NVENC's default preset/quality for a single run (ignored with a log line, not an error, if combined with `--codec h264`).
- **GPU-accelerated filtering** (`--hwaccel`, NVENC codecs only) - without it, the entire pipeline (decode, `delogo`, scale/pad, watermark overlay) runs on CPU and only the final encode touches the GPU; with `--codec hevc`/`av1 --hwaccel`, decode and scale/pad/overlay all run on CUDA (`scale_cuda`/`pad_cuda`/`overlay_cuda`) too - `delogo` still has no CUDA filter in ffmpeg at all, so watermark *removal* specifically still drops to CPU for that one step and re-uploads immediately after. This is what the sidebar's separate "Encoder (NVENC)" reading (see "Key Components" above) is for: without `--hwaccel`, that reading can sit near 0% during a whole render even though the job is genuinely GPU-encoding, because the CPU-bound filters upstream are the actual bottleneck, not the encoder.
- **Encode several files at once, and dial resource usage up or down** (`--parallel <N>`, `--effort low|medium|high`) - `--parallel` (default 1, sequential like before) runs up to `N` files' ffmpeg processes concurrently via a `ThreadPoolExecutor` (each thread just launches and waits on its own subprocess, so the GIL isn't a bottleneck); the batch-wide `render_lock` still wraps the whole run as one unit, same as before, so a `--parallel` run still counts as a single job to the rest of the app (GUI/bot) for cross-process GPU coordination purposes - `run_ffmpeg_with_progress_and_nvenc_retry()`'s existing session-limit retry (see below) already handles two NVENC encodes racing for a limited number of concurrent hardware sessions, so combining `--parallel` with `--codec hevc`/`av1` degrades to a wait-and-retry instead of a hard failure. `--effort` (default `high` = unrestricted, identical to the old behavior) caps `-threads`/`-filter_threads` (`medium` = half the CPU core count, `low` = a fixed 2) - `-filter_threads` matters for *every* codec since the filter graph (scale/pad/watermark/etc.) runs on CPU even when NVENC does the final encode, unless `--hwaccel` is also active; for `hevc`/`av1`, `medium`/`low` also drop to a faster/lighter NVENC preset (`p4`/`p2`) unless `--nvenc-preset` was passed explicitly (which always wins). Useful either to keep the machine usable for other things during a long background batch, or to push a multi-file batch through faster on a machine that can spare the resources.
- **Output framerate & HDR preservation** (`--fps`, HDR handling fully automatic) - `--fps` left unset (the new default) preserves each file's own original framerate exactly, including fractional NTSC rates (`29.97`/`59.94`/`23.976`, read from ffprobe's `r_frame_rate`, falling back to `avg_frame_rate` if that's unusable) instead of forcing every file to a fixed 30fps regardless of source - a batch of mixed-rate clips gets each file's own correct rate, computed per-file in `process_video()` (`resolve_output_fps()` in `utils/video/video_editor.py`), not one global value for the whole run. Pass `--fps <N>` (a plain number or an exact fraction like `30000/1001`) to override for the whole run instead - validated once up front (fails fast on a bad value instead of partway through a batch). Separately, HDR source footage (ffprobe's `color_transfer` reporting `smpte2084`/PQ or `arib-std-b67`/HLG) is detected automatically per file and handled according to `--codec`: with `hevc`/`av1` (NVENC, the only codecs here with real 10-bit/HDR10 metadata support), the output keeps full HDR - 10-bit (`-pix_fmt p010le`) plus the source's exact `-color_primaries`/`-color_trc`/`-colorspace` tags passed straight through unchanged (`--hwaccel` is dropped for that one file only, logged, since the CUDA filter chain here is 8-bit-only); with `h264` (the default codec, no real HDR support in this project), the source instead gets proper HDR-to-SDR tone-mapping (`zscale`+`tonemap=hable`+`zscale` back to `bt709`) before encoding, instead of ffmpeg's naive default of just truncating 10-bit values to 8-bit, which produces a washed-out/dull image rather than an error. `--thumbnail` always tone-maps to SDR regardless of what the main output did - a thumbnail is viewed as a flat image, not on an HDR display, so carrying HDR tags there would only make it look worse.
- **Color grading** (`--lut <path.cube>`, `--auto-levels`) - `--lut` loads a 3D LUT (the common Adobe/DaVinci `.cube` format) via ffmpeg's `lut3d` filter, applied last in the chain (after resize/sharpen - a creative grade over the final-resolution pixels); a missing/unreadable file is logged as a `[WARNING]` and the run continues without it rather than failing the batch. `--auto-levels` applies ffmpeg's `normalize` filter before scaling (stretches each frame's brightness range to full contrast automatically) - useful for dark/flat capture footage that doesn't use the full brightness range.
- **Smooth frame-rate conversion** (`--smooth-fps`) - swaps the plain `fps=` filter for `minterpolate` (real motion-compensated interpolation, generating genuine in-between frames instead of just duplicating/dropping them) - mainly useful when *raising* the rate (e.g. `--fps 60` on a 30fps source); noticeably slower than the default. Ignored with `--hwaccel` (no CUDA `minterpolate` equivalent in this project's ffmpeg build).
- **Noise gate & mid-clip silence removal** (`--noise-gate`, `--remove-mid-silence`, both require `--keep-audio`) - `--noise-gate` applies ffmpeg's `agate` filter before `--loudnorm` (gates out constant background hiss/hum below a threshold without touching speech, then normalizes the gated signal). `--remove-mid-silence` detects *every* silent gap in the clip (not just the start/end like `--trim-silence`) and removes it from video *and* audio together, frame-accurately in sync - a naive audio-only `silenceremove` would shift the audio timeline forward without touching the video and break lip-sync from the first removed gap onward, so this instead builds a matching `select`/`aselect` pair (`utils/video/video_editor.py`'s `build_silence_removal_filters()`) driven by the exact same detected timestamps for both streams, with `setpts=N/FRAME_RATE/TB`/`asetpts=N/SR/TB` renumbering timestamps afterward to close the gaps. Mutually exclusive with `--trim-start`/`--trim-duration`/`--trim-silence` (logged, explicit trim wins) since combining "pick one sub-range" with "remove several scattered ranges" on the same file isn't well-defined.
- **Video stabilization** (`--stabilize`) - two real ffmpeg passes, like `--target-size-mb`'s two-pass mode: `vidstabdetect` analyzes camera-shake and writes a transforms file to a temp path first, then `vidstabtransform` (first filter in the main chain, before even HDR tone-mapping - geometric correction on the rawest frames available) applies the correction during the real render. Adds real time (a full extra analysis pass over the source). Ignored with `--hwaccel` (no CUDA equivalent).
- **Chroma key** (`--chromakey`, `--chromakey-color`/`--chromakey-similarity`/`--chromakey-blend`/`--chromakey-bg-color`) - turns a solid color (default standard green, `0x00FF00`) transparent and composites it over a plain solid-color backdrop (default black) built directly inside the filter graph (ffmpeg's `color=` source filter - no extra image input needed). This is a flat-color background swap, not a background-*image* replacer. Mutually exclusive with `--blur-background` (two different ways to build the base frame; logged, chromakey is ignored if both are given) and not supported with `--hwaccel`.
- **Caption styling** (`--caption-font`, `--caption-font-size`, `--caption-color` as `#RRGGBB`, `--caption-position bottom|top|center`, all relevant only with `--captions`) - `utils/media/captions.py`'s `burn_captions()` used to hard-code Arial/16px/white/bottom; now builds the `force_style=` string from these instead, converting the hex color to ASS's reversed-byte-order format (`_hex_to_ass_color()`) so the flag stays a normal `#RRGGBB` value rather than requiring ASS's own notation. Fixed a real bug found while adding this: caption-burning is a *second* ffmpeg encode pass and previously never passed `-c:v` at all, silently re-encoding with ffmpeg's own default (effectively always `h264`/SDR) regardless of what `--codec`/HDR pass-through the main render actually used - a `--codec hevc --captions` run on HDR source would render correct 10-bit HDR output, then quietly downgrade it back to 8-bit SDR h264 the moment captions were burned in. `burn_captions()` now accepts the same codec/HDR args the main render used and re-applies them.
- **Audio** - dropped by default (`-an`); `--keep-audio` maps it through (mapped directly, without touching it, unless a speed change and/or `--loudnorm` are also active - ffmpeg won't allow a direct stream map on a stream that already went through `-filter_complex`). `--loudnorm` normalizes loudness to the same `-14 LUFS` target `rocket_shorts_publisher.py` uses by default (already includes a `-1.5 dBTP` true-peak ceiling, not just integrated loudness); `--loudnorm-target <LUFS>` overrides that target for a single run (relevant only combined with `--keep-audio --loudnorm`, otherwise logged as ignored). `--captions` burns auto-transcribed captions (`utils/media/captions.py`, `faster-whisper`, the same mechanism `rocket_shorts_publisher.py` already uses for TikTok exports) into the finished output afterward - requires `--keep-audio` (there's nothing to transcribe from an output with no audio track at all, so it's ignored without it rather than guaranteed to fail); a transcription/burn failure (e.g. no speech detected) is logged and skipped, not fatal to the rest of the run. `--captions-translate` (ignored without `--captions`) translates the captions to English instead of transcribing them in the source language - this is Whisper's own built-in `task="translate"` (it only ever translates *to* English, not to an arbitrary target language), so no extra translation API/dependency is involved.
- **Recursive folder-by-folder processing** - `--input_dir` doesn't have to be flat: `find_video_files_by_folder()` (`utils/media/timelapse.py`) walks it with `os.walk`, and every subfolder that directly contains video files is processed as its own group. A folder with subfolders (e.g. one per recording session) gets edited in a single run instead of one `--input_dir` per subfolder. Each subfolder's outputs land in the matching subfolder under `workspace/studio/vertical/` or `workspace/studio/horizontal/` (depending on `--vertical`, mirroring the input's structure), so same-named files in different subfolders never collide; files sitting directly in `--input_dir` itself still land flat in that same `edited_videos/` folder, unchanged from before.
- **Smart re-encode skip** - before rendering, `_compute_current_signature()` hashes *only* the source file's own mtime+size via `utils/video/video_editor.py`'s `compute_render_signature()`. If an output file and a matching `.sig.json` sidecar (see below) with the same signature already exist, the file is skipped entirely (logged as `[SKIP]`, counted in the `RESULT:` line's `skipped` field), regardless of what flags this run passes - useful when re-running the same batch over a folder that only partially changed, or when turning on a new flag (e.g. `--thumbnail`) for new clips shouldn't force every already-processed clip in the same folder to re-render too. Pass `--force` to always re-render a specific run regardless.
- **`.sig.json` sidecars live in their own `_sig/` subfolder** - previously sat right next to each output file (`<output>.sig.json`), cluttering the output folder with a non-video file per clip. `utils/video/video_editor.py`'s `resolve_sig_path()` now puts them under `<output_dir>/_sig/<output filename>.sig.json` instead (same naming precedent as the existing `_previous/` versioning subfolder) - the output folder itself now holds only videos (and thumbnails). Purely a storage-location change: the smart re-encode skip, `--force` versioning snapshot, and everything else that reads/writes this sidecar all resolve the same new path automatically, no behavior difference beyond where the file physically sits.

  This used to also hash every output-affecting flag (codec/watermark/vertical/trim/etc., plus the watermark image's own mtime+size) into the signature, so *any* settings change - even one unrelated to a given file - re-rendered every already-processed clip in the folder. That's gone: only the source file's own content (mtime+size) still breaks the skip, protecting against the one case that genuinely matters (a file replaced in place under the same name - re-recorded footage with the same filename, say - correctly gets re-rendered instead of silently serving the stale old output). Because the signature's format itself changed, the very first run over a folder full of previously-rendered clips after this change still re-renders everything once (the old `.sig.json` files don't match the new hash) - every run after that is settings-independent again.

  Every time a file does *not* skip, `[INFO]` now logs the exact reason (`--force` passed / no prior output / prior output has no `.sig.json` sidecar / source file's mtime+size changed since the stored signature) right there in the run's own output, instead of leaving that to be reverse-engineered later from file timestamps on disk.
- **Two-pass VBR with a target file size** (`--target-size-mb <N>`) - an alternative to the default CQ/CRF quality-first mode, for when you have a concrete size budget (e.g. fitting under Discord's/Twitter's upload limit). `compute_target_bitrate_kbps()` derives a video bitrate from the target size, the clip's duration, and the audio bitrate (if `--keep-audio`); `get_two_pass_codec_args()` then picks the actual encoding strategy per codec - `h264` (libx264) runs two full separate ffmpeg passes (pass 1 writes stats only, discarded to a null muxer; pass 2 does the real encode using those stats), while `hevc`/`av1` (NVENC) get the same effect from a single ffmpeg call using `-multipass fullres` (confirmed present in this project's bundled ffmpeg build for both `hevc_nvenc` and `av1_nvenc` - NVENC has no equivalent of libx264's pass-log files). Ignores `--nvenc-cq` when combined (VBR bitrate targeting and CQ are mutually exclusive rate-control modes).
- **Preview contact-sheet** (`--preview-only`) - instead of rendering, builds one PNG (`utils/video/contact_sheet.py`'s `generate_contact_sheet()`) with a representative frame (at 20% of each clip's duration) and filename for every video that would be processed, arranged in a grid (capped at 5 columns, wrapping to more rows beyond that) - a quick visual sanity check that the right folder/subfolders were selected before committing to a batch render that could take minutes or hours. A clip whose frame can't be extracted gets a plain gray placeholder cell instead of aborting the whole preview. Doesn't touch `render_lock` at all - frame extraction is fast and isn't GPU-contending like a real render.
- **"Time saved with --hwaccel" metric** - the `RESULT:` line now also reports `hwaccel`/`codec`, so `utils/job_history.get_hwaccel_time_comparison()` can compare average seconds-*per-file* (not per-run, so a 50-file batch and a single-file run compare fairly) between runs that used `--hwaccel` and runs that didn't, no new DB column needed since it's already sitting in the existing `result_json` blob. Needs at least one successful run in *both* groups to say anything - returns `None` otherwise, which both UIs treat as "nothing to show yet" rather than an error. Surfaced next to the render-duration stats: the web app's "📊 סטטיסטיקות" dialog (`GET /api/hwaccel_savings`) and the desktop Stats tab (refreshes alongside the job history list).
- **Run summary report** - a `[REPORT]` line is now printed at the end of every batch (created/skipped/errors counts, total wall time, average seconds per created file), and the same numbers (`elapsed_seconds`/`avg_seconds_per_file`) are added to the `RESULT:` JSON - previously the only way to see how long a whole run actually took was indirectly, from `worker.py`'s own external process-timing in `job_history`, not from the run's own output.
- **Automatic retry when NVENC hits its concurrent-session limit** (`utils/media/ffmpeg_progress.py`'s `run_ffmpeg_with_progress_and_nvenc_retry()`) - only for `--codec hevc`/`av1`: if an NVENC render fails with one of a handful of known "session limit reached" error signatures (e.g. another app like OBS is also encoding via NVENC right now, or another parallel file in this same run) rather than some other real failure, it retries instead of failing the file outright - up to 6 times, waiting exponentially longer between attempts (15s, then 27s, 48s, ... capped at 90s, with random ±15% jitter so several files stuck on the same limit don't all retry in lockstep and collide again) instead of a flat 10s wait as before. The real bottleneck freeing up - another parallel file finishing its own full-length 4K encode - can take minutes, not seconds, which the old fixed 10s×3 budget (under a minute total) rarely survived in practice; the new budget stretches to several minutes. Any other failure (bad parameters, no GPU at all) still fails immediately on the first attempt, same as before - this only recognizes that one specific, recoverable situation.
- **Versioning - snapshot before `--force` overwrites** - `--force` used to silently overwrite the previous output. It now first moves the existing output (plus its `.sig.json` and thumbnail, if present) into a timestamped `_previous/` subfolder next to it, so the last version isn't lost to an accidental/unwanted re-render. Keeps only the most recently overwritten version, not a full history - enough to recover from a mistaken `--force`, without accumulating unbounded copies over months of repeated use.
- **Crash-safe atomic output (resumable batches)** - each file now renders to a temporary `<output>.partial.<ext>` path, `os.replace()`'d (atomic on the same filesystem) to the real output path only after ffmpeg genuinely succeeds - a failed/killed render is cleaned up instead of left behind. Previously ffmpeg would still create/open the *final* output path before failing on something like an invalid filter graph, leaving an empty/truncated file there that looked like a completed render to the smart re-encode skip check (`os.path.exists(output_path)` was true even though nothing was actually encoded) - re-running the same batch after a crash now correctly sees "no output yet" for whatever file was in flight and re-renders it, instead of silently treating a broken leftover as done forever.
- **Encode several files at once, and dial resource usage up or down** (`--parallel <N>`, `--effort low|medium|high|auto`) - `--parallel` (default 1, sequential like before) runs up to `N` files' ffmpeg processes concurrently via a `ThreadPoolExecutor` (each thread just launches and waits on its own subprocess, so the GIL isn't a bottleneck); the batch-wide `render_lock` still wraps the whole run as one unit, so a `--parallel` run still counts as a single job to the rest of the app (GUI/bot) for cross-process GPU coordination - the existing NVENC session-limit retry (above) already handles two NVENC encodes racing for a limited number of concurrent hardware sessions, so combining `--parallel` with `--codec hevc`/`av1` degrades to a wait-and-retry instead of a hard failure. `--effort` (default `high` = unrestricted, identical to the old behavior) caps `-threads`/`-filter_threads` (`medium` = half the CPU core count, `low` = a fixed 2) and, for `hevc`/`av1`, drops to a faster/lighter NVENC preset (`p4`/`p2`) unless `--nvenc-preset` was passed explicitly (which always wins). `--effort auto` reads live CPU/GPU load (`utils/shared/hardware.py`'s `get_system_stats()`/`get_gpu_stats()`, the same readings behind the dashboard's CPU/GPU widgets) *per file, not once for the whole batch* and picks low/medium/high from whichever axis is more loaded right now (`resolve_auto_effort()`) - useful for a long background batch on a machine also doing other things, without having to guess one fixed level for the entire run up front.
- **Proactive NVENC concurrency cap, on top of the reactive retry** (`--max-concurrent-nvenc <N>`) - a high `--parallel` combined with `--codec hevc`/`av1` used to mean *every* file tried to open an NVENC encode session at the same instant, so nearly all of them hit "session limit reached" together and had to lean on the retry-and-wait above just to get through a normal run - and on a busy machine could still exhaust even the longer retry budget above and fail outright if the probed limit (measured with tiny throwaway encodes, see below) doesn't hold up under real full-resolution contention. This flag (or its automatic default) caps how many NVENC encodes this run actually launches *at once*, independent of how many files `--parallel` considers in flight - a `threading.Semaphore` held for the file's entire encode (including any retries) rather than a first-come-first-served race. Left unset, the real limit is measured once at startup instead of guessed (`utils/media/nvenc_probe.py`'s `probe_max_concurrent_nvenc_sessions()` - the same probe already used for the diagnostic dialog in both UIs - launches several genuine tiny NVENC encodes simultaneously and counts how many actually succeed together); a value here skips that startup probe and pins the cap directly instead. Irrelevant (and skipped entirely, no probe run) with `--codec h264` (no NVENC involved) or `--parallel 1` (nothing for this run to contend with itself over). If literally no NVENC session could be measured at all (no NVIDIA GPU, or this ffmpeg build lacks NVENC), no cap is applied and the real encode fails for its own, unrelated reason on every file, same as before this flag existed.
- **Export container** (`--container mp4|mkv`) - `mkv` (Matroska) is a fully flexible container that accepts every codec combination used here (h264/hevc/av1 + aac) with no other changes needed - ffmpeg picks the muxer from the output file's extension by itself. `webm` is deliberately not offered: it only accepts vp8/vp9/av1 video and vorbis/opus audio, so it's incompatible with h264/hevc/aac outright, not just "not implemented yet".
- **Custom output filename template** (`--output-template "{name}_{codec}_{date}"`) - overrides the default `<name>_edited_horizontal/vertical.mp4` naming (and `--no-suffix`, which it takes priority over) with placeholders resolved per file without needing to probe it first: `{name}` (source filename), `{codec}`, `{orientation}` (horizontal/vertical), `{date}` (`YYYYMMDD`, wall-clock at render time), `{number}` (see `--number-videos` below, blank if not active). An unknown placeholder is rejected once up front (`utils/video/video_editor.py`'s `validate_output_template()`) before any rendering starts, not partway through a batch.
- **Sequential video numbering** (`--number-videos`, `--number-prefix <text>` default `Clip`, `--number-start <N>`) - same persistent-counter naming scheme `rocket_shorts_publisher.py` already uses for its own output filenames (e.g. `Shorts #42`), so a related pipeline that also numbers its outputs (thumbnails for a numbered episode series, say) can pick up where a previous run left off instead of restarting from 1 - but tracked in its own separate, dedicated counter file (`data/video_editor_counter.txt`, `utils/video/video_editor_counter.py`) rather than sharing `rocket_shorts_publisher.py`'s `data/counter.txt`, so the two pipelines' numbering never interferes with each other. Without an explicit `--output-template`, `--number-videos` implies the naming template `"{prefix} #{number}"` (e.g. `Clip #7.mp4`), taking priority over `--no-suffix`/the default `<name>_edited_...` naming (same precedence `--output-template` itself already has - an explicit `--output-template` still wins over both). `--number-start <N>` only seeds the counter the very first time it's ever used (no counter file yet) - after that, changing it in the desktop/web settings panel resets the counter for real, immediately (see "manual counter reset" below), not by re-passing `--number-start` on the next run.
  - **Smart re-encode skip stays correct even with numbering active** - the numbered output filename changes on every run (the counter always advances), so it can't itself be used to detect "this exact source file was already rendered". The skip check for a numbered run is instead keyed off a stable identity (source filename/orientation/container, independent of the number), so restarting a batch that already finished successfully now correctly skips everything instead of re-rendering *and* re-numbering the whole folder from scratch - which used to be the main way this counter drifted far ahead of where it should be after a batch was started/stopped a few times.
  - **The counter only advances past numbers that produced real output** - a number is still reserved (and persisted immediately) before that file renders, so two files under `--parallel` can never race for the same number and a genuine process kill mid-batch can never hand out a number twice. But once the batch finishes (even with some files failing) `persist_final_counter_value()` corrects the saved counter down to one past the *highest number that actually got a successful output file* - a failed file's number is returned to the pool instead of being burned forever, as long as *some* later file in the same run didn't also succeed at a higher number (in which case that higher number is what's kept, to never collide with the file that already exists there). A batch where nothing at all succeeded rolls all the way back to where the run started. An abrupt external kill (e.g. the GUI's Stop button) still can't be corrected after the fact - the last number reserved before the kill stays burned, same as before.
  - **Manual counter reset** - editing "מספר התחלתי"/"start number" in the desktop or web settings panel and moving focus away resets `data/video_editor_counter.txt` to that value immediately (`utils/video/video_editor_counter.py`'s `save_number()`, called directly - not via the `--number-start` CLI flag, which is ignored once the counter file already exists), so a manual correction (e.g. after cleaning up a batch that numbered itself further than expected) takes effect right away instead of silently doing nothing until the counter file is deleted. Only fires when the typed value actually differs from what was there before, so unrelated settings edits/focus changes never reset it by accident. `--validate-only` runs reserve no number at all (nothing is actually being produced, so nothing should advance the persistent counter).
- **Validate a batch's filter graphs before committing to a full render** (`--validate-only`) - runs the *exact* real command (filters, watermark, HDR, LUT, everything) for each file but truncated to 0.3 seconds and muxed to `null` instead of a real output, reporting `[VALID]`/`[INVALID]` per file (and `valid`/`invalid` counts in the final `RESULT:` line) instead of rendering for real - catches a bad flag combination (a malformed LUT, an invalid crop expression) across an entire folder in seconds instead of discovering it after the first file of an hours-long batch fails. Ignores the smart re-encode skip and `--force` entirely - every file is checked regardless of whether it already has a rendered output.
- **Per-file notifications** (`--notify-per-file`) - sends a Windows toast (`utils/shared/notifications.py`'s `send_toast_notification()`) and, if a Discord webhook URL is already configured (`state.discord_webhook_url`), a webhook message (`send_webhook_notification()`) for *every* file as it finishes (success or failure) instead of only one summary notification at the very end of the whole batch - useful for a long-running batch where you want to know as soon as a specific file is done, not just when everything is.
- **Picture-in-picture overlay** (`--pip <path>`, `--pip-position` (same choices as `--watermark_position`), `--pip-scale` (default `0.3` = 30% of output width), `--pip-opacity`) - composites a second *video* (not a static image, unlike the watermark) as a small layer on top of the main output, geometry computed by the same `compute_watermark_geometry()` the watermark uses (probing the PiP file's own dimensions via `ffprobe`/`probe_video()` instead of `PIL.Image.open()`, since it's a video, not a single frame). Builds as a second `overlay` stage in `build_edit_filter_complex()`, inserted *before* the watermark overlay when both are given (watermark - the branding layer - always ends up on top/last) - input indices are computed dynamically rather than hardcoded, since PiP always claims input index 1 (right after the main video) when present, pushing the watermark's own `-i` to index 2 instead of its previous fixed index 1. Not supported with `--hwaccel` (no proven CUDA equivalent in this project, same as chroma key/blurred background/stabilization above) - ignored with a log line, same pattern as those.
- **Smart crop by face detection, as an alternative to motion-based smart crop** (`--smart-crop-face`, requires `--smart-crop` already active) - `utils/media/smart_crop.py`'s `compute_horizontal_crop_offset_face()` uses OpenCV's DNN-based `cv2.FaceDetectorYN` (the YuNet model, bundled at `assets/face_detection_yunet_2023mar.onnx` under Apache 2.0, since this project's installed `opencv-python` 5.x dropped the older `cv2.CascadeClassifier`/Haar-cascade API entirely - there's no cascade XML to fall back to even if one were bundled) instead of `compute_horizontal_crop_offset()`'s frame-diff motion analysis, weighting each detected face's x-position by the detector's own confidence score across ~15 sampled frames (fewer than motion's 40 - DNN inference per frame is considerably more expensive than a plain `absdiff`). Same `-1.0..1.0` return contract and same "falls back to 0.0/centered on any failure, including a missing model file" guarantee as the motion-based function, so a talking-head clip with no clearly detected face degrades to a normal center crop rather than failing the file. Best suited to interview/talking-head footage, where the subject matters more than general on-screen motion.
- **Editable per-run file queue** (`--only-files '["b.mp4", "a.mp4"]'`, a JSON array of filenames) - restricts (and reorders) which files get processed from the *root* of `--input_dir` for this one run, leaving any subfolders (`find_video_files_by_folder()`'s recursive groups) completely untouched - the queue editor described below only ever shows/edits the root folder's own files. A name in the list that doesn't match an actual video file there is silently ignored (not an error); invalid/non-JSON input logs a `[WARNING]` and falls back to processing every file in the root, same as not passing the flag at all.
- **Export a run report to CSV/Excel** (`--export-report csv|xlsx|both`) - writes a summary (run duration, average seconds/file, created/skipped/error counts, codec/container/hwaccel/parallel/effort) plus one row per file actually created (source/output filename, codec, container, resolution, fps, duration, output size in MB, that file's own render time, HDR) to `workspace/reports/video_editor_report_<timestamp>.csv`/`.xlsx` - a shared subfolder directly under `workspace/`, not nested under `horizontal`/`vertical`, since one report can describe a batch that touched either. The `.xlsx` is a real formatted workbook (`utils/video/video_editor_report.py`, reusing `utils/shared/report_excel.py`'s `style_sheet()` - the same RTL/bold-header/auto-filter/freeze-panes styling already used for `disk_scanner.py`'s Excel reports, not a one-off): a "סיכום" (summary) sheet and a "קבצים" (files) sheet. The `.csv` has the same two sections (summary key/value rows, then a blank line, then the files table) written with a UTF-8 BOM so Excel opens the Hebrew headers correctly instead of mangling them. **Personal profiles** - beyond the four built-in, fixed presets above the watermark fields (a "type of edit": vertical/target-seconds/keep-audio/loudnorm/codec only, no paths, sourced from `utils/video/video_editor.py`'s `VIDEO_EDITOR_PRESETS`), the same dropdown also lists profiles the user creates themselves (`utils/video/video_editor_profiles.py`, `data/video_editor_profiles.json`): a full snapshot of every field in the panel, watermark path/position/opacity included, saved under a name typed into the field next to "💾 שמור פרופיל"/"Save profile". Selecting one (marked "👤 " on desktop, since `CTkOptionMenu` has no `<optgroup>`; a separate "הפרופילים שלי"/"My profiles" group in the `<select>` on the web) fills in every field at once and reveals "🔄 עדכן"/"Update", "✏️ שנה שם"/"Rename", and "🗑️ מחק"/"Delete" buttons next to the dropdown. Unlike the rest of this panel, profiles are shared between both UIs through the same JSON file - one saved from the browser shows up in the desktop GUI's dropdown next time that panel is opened, and vice versa, no restart needed on either side.
- **Update an existing profile in place** (item) - "🔄 עדכן"/"Update" re-saves the *currently selected* profile with whatever the form holds right now, under the exact same name, with no retyping required. Both UIs already overwrote a profile if you saved a new one under a name that already existed (`utils/video/video_editor_profiles.py`'s `save_profile()` always overwrites-if-exists, and the web's `POST /api/video_editor_profiles` never had a distinct "update" route to begin with - the JS `updateVideoEditorProfile()` just resends the identical save request with the already-selected name) - this button only makes that existing overwrite-by-name behavior reachable as an explicit one-click action instead of requiring you to retype the profile's name exactly to get the same effect. Hidden whenever no personal profile is currently selected (a built-in preset or the placeholder), same visibility rule as the existing delete button.
- **Rename a profile** (item) - "✏️ שנה שם"/"Rename" (`utils/video/video_editor_profiles.py`'s `rename_profile()`) moves a profile's settings to a new name without retyping/re-saving every field. Desktop prompts via `ctk.CTkInputDialog` (no pre-filled default - the built-in dialog doesn't support one); the web uses the browser's native `prompt()` pre-filled with the current name instead, since that one does. Deliberately different from `save_profile()`'s silent-overwrite-by-same-name behavior above: renaming *into* a name already taken by a *different* profile always raises instead of silently merging the two - accidentally merging two unrelated profiles into one is a much more surprising failure mode than the "update a profile under its own name" case `save_profile()` already handles safely. Renaming into the profile's own current name (or cancelling the prompt) is a no-op, not an error.
- **Folder saved as part of a profile** (item) - a profile snapshot now also includes the currently-selected input folder (`folder`), restored along with every other field when that profile is selected. This one field deliberately breaks the otherwise-uniform `video_editor_<field>` naming convention every other field in `PROFILE_FIELDS` follows: the input folder (`state.selected_gameplay_folder` on desktop, `state.folder` on the web) is a single value shared by *every* script in the app, not something specific to the video editor, so both UIs collect/restore it as an explicit special case rather than through the generic per-field loop the rest of the panel uses. An older profile saved before this feature has no `folder` key at all and simply leaves the currently-selected folder untouched when loaded, rather than clearing it to blank.
- **Confirmation after saving/updating a profile** (item) - "💾 שמור פרופיל"/"Save profile" and "🔄 עדכן"/"Update" used to give no feedback beyond the dropdown/buttons appearing, easy to miss - both now show an explicit confirmation (`messagebox.showinfo()` on desktop, `alert()` on the web) naming the profile once the save actually succeeds.
- **Duplicate a profile / "save as"** (item, web-only) - "🔀 שמור בשם..." copies the currently-selected profile's settings under a new name and switches to it, leaving the source untouched (unlike "🔄 עדכן", which overwrites the current one). The copy starts with fresh usage stats (`run_count=0`) - it's a new profile's first use, not a continuation of the source's history.
- **Export/import a single profile as JSON** (item, web-only) - "⬇️ ייצוא" downloads one profile's settings as a standalone `.json` file (a clean `PROFILE_FIELDS` snapshot, no usage metadata - not meaningful on another machine/user); "⬆️ ייבוא פרופיל..." reads one back in, asking to confirm before overwriting a profile that already exists under the same name.
- **Compare two profiles** (item, web-only) - "🔍 השווה פרופילים..." shows only the fields that actually differ between two selected profiles (labeled with the same short terms as the glossary), not a full side-by-side dump of every field - useful with ~48 possible fields where most are usually identical.
- **Last-used timestamp and run count per profile** (item, web-only) - selecting a personal profile shows "🕒 בשימוש לאחרונה: <date> · N הרצות" once it's actually been used to run a render at least once (never-used profiles show nothing, not a confusing "never"). Recorded server-side (`record_profile_used()`) when `/api/run` actually dispatches `video_editor.py` with that profile selected, not just when the profile is loaded into the form.
- **Undo history for a profile** (item, web-only) - every time an *existing* profile is overwritten (via "🔄 עדכן" or a same-name "💾 שמור פרופיל"), its previous settings are pushed onto a per-profile history (`data/video_editor_profile_history.json`, capped at the 5 most recent). "↩️ היסטוריה" lists past versions with a one-click "↩️ שחזר" - reverting itself pushes the pre-revert state onto the same history first, so a revert can be undone too.
- **Explicit profile schema version** (item, web-only) - every save now stamps the profile with the current `PROFILE_FIELDS` schema version (`data/video_editor_profile_meta.json`) - groundwork for cleanly migrating older saved profiles if fields are ever added/removed/renamed later, not a migration that exists yet (there's only been one version so far).

**Faster timelapse rendering for long recordings** (item) - investigated a report that `--target-seconds` (timelapse) could take hours on long gameplay recordings. Root cause: `setpts=PTS/<factor>` (the speed-up) ran through the *entire* per-frame chain (scale, watermark overlay, sharpen, LUT) before the final `fps=` filter dropped the ~95%+ of frames a high speed-up factor discards - `fps=` only depends on frame *timing* (PTS), not content, so reordering it to run immediately after `setpts` (before scale/watermark/sharpen/LUT) produces byte-identical output while skipping that per-frame work for the frames about to be dropped anyway. Guarded to only apply when nothing temporally-sensitive is also active (`denoise`/`stabilize`/silence-removal/`smooth_fps` genuinely need frames in their original decoded order/spacing; chromakey/blur_background build a separate filter graph) and never with `--hwaccel`. Measured on a synthetic 1080p→540p scale+sharpen timelapse at speed-factor 9: 4.47s → 2.09s (~2.1x) for the filter+encode portion. Decode time itself (the actual dominant cost for hours of source footage) is unaffected by filter order and unchanged by this fix - see the roadmap for the larger, separate idea of decoupling hardware-accelerated *decode* from the NVENC-only `--hwaccel` path, which would address that remaining piece.

**Fade-in/fade-out** (item) - `--fade-in-seconds`/`--fade-out-seconds` apply ffmpeg's `fade`/`afade` filters as the *very last* stage on both video and audio, after watermark/PiP compositing (so branding layers also darken/lighten, not just the base frame). Fade-out needs the actual output duration (post-trim/timelapse) to compute when it starts - `st=duration-fade_out_seconds` - so it's silently skipped if that isn't available.

**Static text overlay** (item: `--text`/`--text-position`/`--text-font`/`--text-font-size`/`--text-color`) - burns a fixed caption/lower-third into every frame, applied right before any fade so the text also fades with the rest of the frame. Different from `--captions` (auto-transcribed, changes over time) - this is one static string for the whole clip. Implemented via drawtext's `textfile=` (the text is written to a small temp file, one per run, not embedded inline in the filter string) with `expansion=none` - found in practice that embedding arbitrary user text directly into the filter_complex string required an unintuitive escaping+quoting combination that still silently corrupted a `'` when combined with a `:` in the same string, and drawtext's own `%{...}` expression syntax broke on a raw `%` unless expansion is explicitly disabled; `textfile=` sidesteps all of that since the text content never touches the filtergraph's own parser at all.

**Replace audio track** (item: `--replace-audio <path>`) - mutes the original audio entirely and maps a separate audio/video file's audio stream in its place (not mixed). Automatically enables `--keep-audio` if not already set (replacing audio you're not keeping in the output would be a no-op). The replacement file becomes an additional ffmpeg input, positioned after any watermark/PiP inputs - the exact index is computed per-file so it stays correct across every input combination.

**Cut multiple ranges from one clip** (item: `--remove-ranges`, a JSON array of `[start,end]` pairs in seconds) - reuses the existing `--remove-mid-silence` mechanism (`select`/`aselect` with a synchronized video+audio boolean condition) rather than adding a second one - user-specified ranges simply merge into the same removal list as auto-detected silence, so both can be used together. Mutually exclusive with `--trim-start`/`--trim-duration`/`--trim-silence`, same reasoning as `--remove-mid-silence`: those all mean "pick one continuous sub-range," this means "remove several scattered ones."

**Per-file flag overrides for a whole batch run** (item: `--batch-overrides <path-to-json>`, `{"filename.mp4": {"watermark_path": "...", "trim_start": 5}, ...}`) - deliberately scoped to `watermark_path`/`watermark_position`/`watermark_opacity`/`watermark_scale`/`trim_start`/`trim_duration` only (the roadmap's own example), not a fully generic per-file override of all ~50 settings. Implemented as explicit function parameters resolved to local variables at the top of `process_video()`, not a temporary global-variable monkey-patch - `--parallel` runs files on real separate threads, so mutating shared module-level globals per-file would have been a genuine data race between concurrently-rendering files.

**Hardware-accelerated decode without requiring NVENC output** (item: `--hwaccel-decode`) - the existing `--hwaccel` bundles GPU decode *and* NVENC encode together (requires `--codec hevc/av1`); this is decode-only, works with any codec including the default `h264` (CPU). Frames come off the GPU (`hwdownload,format=nv12`) as the very first filter stage, before anything else runs - from that point on the rest of the chain is byte-for-byte the same CPU path as without `--hwaccel-decode` at all, so it composes safely with every other filter (watermark, LUT, chromakey, etc.) without needing CUDA-native equivalents for each one. Falls back silently on HDR sources (same 8-bit-only limitation as `--hwaccel`, and tone-mapping needs the full decoded bit depth to work correctly) and is ignored if `--hwaccel` is already active. Measured on real NVIDIA hardware (RTX 4070 SUPER) with a 90-second 1080p synthetic clip + `--sharpen`: 40.6s → 18.1s (~2.2x) for the decode+filter+encode portion - decode is frequently the dominant cost for long recordings, and this now lets you keep it while staying on `h264` for compatibility.

**Stitch multiple clips into one with crossfade/dissolve transitions** (item: `--concat-files`, a JSON array of filenames/paths, ordered) - a deliberately separate run mode (`run_concat_mode()`, bypassing the normal per-file folder loop entirely) rather than a new flag on the existing per-file pipeline, since "merge N inputs into one output" doesn't fit a script built around "one input → one output" at all. Every clip is scaled to common output dimensions first (`--vertical` picks horizontal/vertical, same as the regular path) since `xfade`/`concat` both require matching dimensions across inputs. `--concat-transition fade` (default - "crossfade"/"dissolve" are the same thing, just two names for it) chains `xfade` (video) and `acrossfade` (audio) across all clips, with each transition's `offset` computed from the running merged-duration-so-far minus the transition length (`compute_xfade_offsets()`, a small pure function kept separate specifically so the offset math has its own unit tests independent of filter-string construction); `--concat-transition none` uses plain `concat` instead, no overlap. Verified against real ffmpeg with solid-color test clips and pixel-sampled crossfade timing (a two-color 50/50 blend appeared at exactly the computed transition midpoint, not approximately). Deliberately narrow in scope: no watermark/LUT/trim/etc. on the clips being merged - it's a "stitch these together" operation, not a full per-clip editing pass combined with concatenation.

**Wave 22 - stability and safety (27.9.2026).**

- **One owner for the editor's async flow** - `frontend/js/07-ui-flow.js` adds `veFlow`, which owns the folder → project → profile → queue sequence. **Wave 24 - performance (27.9.2026).**

- **CSS and JS as cached static files** - the page used to inline all its CSS and JS, so every load sent about 1 MB. Now `web/frontend_assembly.py` builds two bundles from `parts.txt`, `/static/app.<hash>.css` and `/static/app.<hash>.js`. The name is a hash of the content, so the browser caches them for good (`immutable`) and a code change always gets a new name. The bundles and the HTML are gzipped once at startup. A repeat load now downloads only the HTML (about 34 KB compressed instead of about 1 MB), and a first load about 245 KB. The HTML itself is `no-cache`, so it always points at the current bundles, and an unknown or old hash returns 404 rather than different content under a cached name. `CLIPFORGE_DEV_RELOAD_PAGE=1` still rebuilds everything on each request. Tests that check page content read the HTML plus both bundles (`tests/page_source.py`) or `assemble_inline_page()`, and the size budget checks the HTML, the JS and the compressed total separately.
- **A bounded pool for the server's own ffmpeg calls** - thumbnails, probes, source frames, the timeline strip, previews and settings checks, the player proxy, and scene and loudness analysis used to call `subprocess.run` directly from the routes, so a folder of hundreds of files could start dozens of ffmpeg processes at once, in the middle of a render. `utils/video/media_pool.py` runs them in three lanes with their own limits: thumbnails and probes (2-4, by CPU count), interactive work the user is waiting for (2) and background analysis (2). A flood of thumbnails can't hold up a preview. Two requests for the same thumbnail or timeline strip (from the queue, the jobs screen and the home screen) run ffmpeg once, and the second waits for the file instead of reading it half-written.
- **The queue updates only what changed** - checking a box or clicking a row used to rebuild every row of the queue (hundreds of rows with a thumbnail and event listeners each). Each row is now kept per queue item with a signature of what it shows. Only rows whose signature changed are rebuilt, in place, a rebuilt row keeps its existing thumbnail, and rows move only when the order actually changed. `tests/web/test_web_app_wave24_browser.py` checks this in a 300-file queue, and that the bundles come from the browser cache on the next load.

**Wave 25 - pro color and audio tools (27.9.2026).**

- **Color wheels (lift / gamma / gain)** - three wheels in the Look area (advanced mode) tint the shadows, midtones and highlights: drag picks the hue, the distance from the center is the strength (Shift for fine moves, arrow keys and Delete from the keyboard, double-click to reset), and a slider under each wheel brightens or darkens only that range. Each wheel is stored as an `R,G,B` offset (`--grade-shadows`, `--grade-midtones`, `--grade-highlights`, -1 to 1) that you can also type, and renders with ffmpeg's `colorbalance`.
- **Curves** - a curve editor for the master tone and for R, G and B separately (click adds a point, drag moves it, double-click deletes it), plus ffmpeg's curve presets (lighter, darker, four contrast levels, vintage, cross process, color negative). Points you set override the preset on the same channel. Stored as `x/y` point lists (`--curves-master`, `--curves-red`, `--curves-green`, `--curves-blue`, `--curves-preset`). The grade runs right after brightness/contrast/saturation, as CPU filters, so with the full GPU pipeline filtering moves to the CPU the same way it does for the other color settings.
- **The live player shows the grade** - the wheels and curves are previewed in real time through an SVG filter with a per-channel color table computed the same way as `colorbalance` and `curves`. Without a grade no filter is applied.
- **Audio processing** - in the Sound area: a low cut (`--audio-highpass`, 0 = off, 80 Hz suits speech), a three-band EQ (`--audio-eq-low` around 120 Hz, `--audio-eq-mid` with `--audio-eq-mid-freq`, `--audio-eq-high` around 8 kHz, in dB), a compressor with gentle / voice / strong settings (`--audio-compressor`) and noise reduction (`--audio-denoise`, light / medium / strong) with ffmpeg's `afftdn`. If you point `--audio-denoise-model` at an RNNoise model file (`.rnnn`), the neural `arnndn` filter tuned for speech is used instead - the project doesn't ship a model, so download one yourself (for example from the RNNoise models collection) if you want it. The chain runs low cut → noise reduction → EQ → compressor, after speed changes and before the noise gate and loudness normalization, and only when the output keeps audio (the editor warns otherwise).
- **Checks and translation** - `utils/video/color_audio.py` builds all the filters and parses the wheel and curve values; the same parser flags a bad value next to the field before a run, and ffmpeg errors from `curves`, `colorbalance`, `arnndn` or the audio filters point back to the right field. All the new controls are in English mode too. `tests/studio/test_color_audio.py` runs every filter through the real ffmpeg and renders a clip with everything on; `tests/web/test_web_app_wave25_browser.py` drags the wheels, draws curves, restores them from a profile and checks the live preview.

**Wave 26 - B-roll inside the timeline (27.9.2026).**

- **A second clip for a time range** - the layers editor has a new 🎞️ B-roll layer: a video clip that plays inside the output from a start time to an end time (output time, like every layer), from a chosen point in the clip. It can fill the frame (cropped to fit), fit inside it (with borders) or sit in a window (PiP) with its own size and position, which you can also drag on the preview. Without an end it runs until the clip or the output ends, whichever comes first, so the output keeps its length. Concatenating clips back to back was already possible; this cuts away to other footage and back.
- **Its audio** - muted (the main audio continues underneath), mixed with the main audio, or instead of it for that range (the main audio is silenced in the range and comes back after). A clip without audio is simply not mixed.
- **Rendering** - `utils/video/video_editor_layers.py` seeks straight to the in-point and reads only the needed length (`-ss`/`-t` on the input), shifts the clip to its start time, scales it for the chosen framing and overlays it only inside its range (`eof_action=pass`); the audio is delayed to the same start and mixed after the rest of the audio chain (EQ, compressor, loudness). Layers still force CPU filtering with the full GPU pipeline, as before.
- **In the editor** - the timeline's layers track shows the clip's name, the live player plays the B-roll muted and in sync with the output time (its audio is heard only in the render), and a missing clip is flagged next to the layers field before a run. `tests/studio/test_broll_layers.py` renders a real clip and checks the B-roll frame appears only inside its range, the length and the audio; `tests/web/test_web_app_wave26_browser.py` covers the editor row, the drag handle and the live player.

- **Targets** - "target" next to ▶ run: YouTube (16:9, as the episode is set), **YouTube Shorts** or **TikTok** (a vertical 1080x1920 frame, with margins and the timeline laid out for portrait, written as `<name>_shorts.mp4` / `<name>_tiktok.mp4` so it never replaces the horizontal video). `dataviz_maker.py --target shorts`; `src/dataviz/targets.py`.
- **A queue of episodes** - a "queue" tick on every episode card; "▶ render N episodes in a row" sends them all in one run (`dataviz_maker.py --episodes a,b`), one after another, with the same mode and target.
- **Duplicate and next in series** - "⧉ duplicate episode" copies the folder under a new name (files and browser changes; the original is untouched, an existing name is refused), and "➕ next in series" also raises the series number. A series (`series: {name, number}` in the config) shows as a badge on the card.
- **New episode from a template** - "template" in the new-episode form: design, pacing, ranking, labels, outro, colors, logo and series (number + 1) come from an existing episode; title, data and events come from the new file. The value and group columns of a new file are guessed (the first numeric and the first text column), so a CSV turns into a running episode in three clicks.
- **Channel kits** - "🏷️ channel kit": a theme, colors, palette and a logo in a corner (`logo: {path, position, scale, opacity}`), saved in `data/dataviz_kits.json`. A kit is made from an episode or imported from a super-editor brand kit (its watermark becomes the logo), and applying it to an episode writes to that episode's override file only.
- **Outputs** - tick "⇆ compare" on two videos and play them side by side (the second follows the first); "🗑️ move to Recycle Bin" sends a video with its package, SEO sheet and thumbnail to the Windows Recycle Bin (restorable).
- **Publishing inside the screen** - "📦 publish this episode" lists the selected episode's packages, and the **publish wizard** walks through them: texts (YouTube title, description, TikTok caption, hashtags - editable until the package is sent, `POST /api/dataviz/packages/{o}/{n}/metadata`), thumbnail, approval, and sending - dry run, Rocket Shorts, or a private YouTube upload with an optional **scheduled publish time** (YouTube makes it public by itself). A sent package shows a link to the video and the scheduled time.
- `tests/dataviz/test_dataviz_series_publish.py` covers targets, the run arguments, duplicating, templates, kits, the Recycle Bin and package texts / scheduling; `tests/dataviz/test_web_app_wave41_browser.py` covers the queue with a target, next in series, kits, compare and Recycle Bin, the wizard (dry run only), and the click budget from a CSV to a running episode.

**Wave 42 - the graph editor: the engine (15.10.2026).**

- **Map chart** (`map_race`) - each region of a GeoJSON file in the episode folder (`map: {geojson, key}`) is colored by the cumulative value of the entity with the same name, with the ranking beside the map (`src/dataviz/geo.py`, `charts/map_race.py`). The data check lists entities that have no region on the map. It appears in the chart lists of the screen, and in the chart comparison only for an episode with a map file.
- **Captions** - `captions.enabled` (or `--captions`) writes `<name>.srt` next to the video: one caption per event card and per "new record", at exactly the frames they are on screen (computed from the plan, `src/dataviz/captions.py`). "💬 captions (SRT)" downloads the file for the full video without rendering (`GET /api/dataviz/episodes/captions`).
- **Narration** - `narration.enabled`: a Windows voice (SAPI through PowerShell, no extra packages) reads each event when its card appears, in full and test videos; ffmpeg mixes the lines over the music without lowering it and copies the video stream. Voice, rate, volume and whether records are read too are settings; a failure keeps the video as it was (`src/dataviz/narration.py`, `GET /api/dataviz/voices`).
- **Picture and GIF for sharing** - a new mode, "share": the strongest moment is the day with the biggest jump; `share.png` (full size) and a short `share.gif` around it (`share.gif_seconds`, `gif_fps`, `gif_scale`) are written to `<name>_share/`, without ffmpeg (`src/dataviz/share.py`). They show up with the outputs.
- **Engine guide** - "📖 engine guide" on the screen: chart types, modes, targets, captions / narration / map / branding, every setting (label, explanation, range and default - built from the schema, so it never goes stale), the command line, and the Windows voices on this computer, with search (`src/dataviz/help.py`, `GET /api/dataviz/help`).
- Everything is off by default, so existing episodes render exactly as before. `tests/dataviz/test_dataviz_wave42.py` covers captions and SRT, narration (lines, fake WAVs, the ffmpeg mix and keeping the video on failure), the strongest moment and the share files, GeoJSON and the map chart, the data check, the guide and the routes; `tests/dataviz/test_web_app_wave42_browser.py` covers the guide, share mode, the map in the chart lists and the captions download.

**Wave 43 - the graph editor: look and data leftovers (16.10.2026).**

- **Contrast check** - the colors tab checks the text (4.5:1), the accent color (3:1) and the palette / fixed entity colors (2:1 - bars and areas are large) against the background, and updates with every color change before saving.
- **Font** - a font picker in the colors tab (the installed fonts the engine knows, `GET /api/dataviz/fonts`), saved as `theme_overrides.fonts` (names only, with fallbacks).

- **Updating data** works for Excel and JSON sources as well: the new data is saved as a new CSV file and the source switches to CSV with the same column mapping; the original file is untouched.

**Wave 44 - the graph editor: publishing and queue leftovers (16.10.2026).**

**Wave 45 - the graph editor: engine leftovers (16.10.2026).**

- **Before / after in the engine guide** - every number, choice and yes/no setting has "👁 before / after": two frames of the selected episode at the current moment, with the default and with another value (a draft only - nothing is saved).
- **Recorded narration** - a "🎙 narration" tab in the full editor records your own voice for each event from the microphone; every recording is a new file under `data/dataviz_overrides/<episode>/narration/<date>_<time>.webm` (the newest wins, "🗑" sends one to the Recycle Bin), and the episode points to the folder (`narration.folder`). **Wave 47 - the remaining open items (16.10.2026).**

- **City boundaries / shapefiles** - the map library also takes a zipped shapefile (`.shp` + `.dbf`, with `.cpg` when present - Hebrew in cp1255 works without it): polygons and holes are read without extra libraries and saved as a new GeoJSON map (`POST /api/dataviz/maps/upload_shapefile`, `dataviz.geo.shapefile_to_geojson`, `utils/dataviz_library.save_shapefile_zip`; at most 30MB zipped / 120MB unzipped). **Wave 48 - process_video on a settings object (16.10.2026).**

- `process_video` (`my_scripts/video/video_editor.py`) no longer reads the ~85 run globals: everything it uses comes from `cfg`, a `RenderConfig` that holds the values derived from the flags (built once as `RENDER_CONFIG`, after all of them are set, together with `SETTINGS` and `HWACCEL_REQUESTED`). Identical commands mean identical videos. A deliberate command change is recorded with `uv run python -m tests.video_editor_golden --write`.
